# MiniMax-H3 768p: Trainium2 vs 8×H200 vs 8×H100, on one method and one set of prompts (2026-11-03)

Every row below ran the **original bench_768p method** (`60d1bf3`): API serving, client wall clock, 1 excluded warmup + 5 back-to-back requests, 1344×768 / 124 frames / 50 steps / flow shift 12 + audio shift 3. Every stack sent **the same requests**, prompt and seed character for character:

| request | prompt / input | seed | why |
|---|---|---|---|
| **`t2va`** | the original reference request: "Night-vision bedroom footage: while the owner sleeps, three cats burst in playing tiny brass instruments at full volume, freeze, then march out as if nothing happened." | 1101 | the baseline (`req_768p.py`, 41.81 s on 2026-10-21) |
| `t2va_parrot` | "A sun conure parrot springs off a pale perch, …" | 42 | vllm-omni-neuron's own E2E / `run.py` request |
| `t2va_atnight` | "At night, three cats march into a bedroom playing tiny brass instruments, …" | 1101 | the vllm-omni reference prompt, which the 2026-10 vllm-omni and Trn2 API rows used |
| **`fl2va`** | vllm-omni-neuron #436's case: the HF model card's reproducible 768p fl2va request (`assets_fl2va/`) | 0 | the fl2va baseline |

Until now the three stacks had not been on one prompt: sglang used the Night-vision text, vllm-omni and the Trn2 API runs the At-night one, and the Trn2 E2E numbers the parrot one. The rows below show that the prompt is not what moves the numbers (±0.2 s on every stack).

## Results

**8× H200** (p5en.48xlarge spot, us-west-2d, driver 595.112.07), Ulysses 8. `h200_aligned_20261103/`, `run_h200_aligned.sh`.

| stack | `t2va` | `t2va_parrot` | `t2va_atnight` | `fl2va` | peak / GPU |
|---|---|---|---|---|---|
| sglang `dev` (`797af7170`), exact | **37.98 s** | 37.99 s | 37.99 s | **42.47 s** | 82,460 MB (fl2va 82,656) |
| vllm-omni 0.29.0rc1 + vllm 0.29.0 | **39.35 s** | 39.43 s | 39.42 s | **44.51 s** | |

**8× H100 80GB** (p5.48xlarge spot, us-east-2b, driver 595.112.07). `h100_20261103/`, `run_h100_*.sh`.

| stack | parallelism | `t2va` | `t2va_parrot` | `t2va_atnight` | `fl2va` | peak / GPU |
|---|---|---|---|---|---|---|
| sglang `dev` (`38d9e4a3f`), exact | TP2 × Ulysses 4 | **40.30 s** | 40.34 s | 40.35 s | **45.21 s** | 51,454 MB |
| vllm-omni 0.29 | HSDP 8 | **45.55 s** | 45.63 s | 45.61 s | **51.25 s** | |

- Ulysses 8 alone does not fit an 80 GB card: the 62 GB DiT is replicated (H200 peaks at 82.5 GB). sglang shards it with `--tp-size 2`.
- vllm-omni 0.29 accepts `--tensor-parallel-size 2`, but its H3 DiT is not TP-sharded, so TP2 × U4 OOMs at load like U8 does. `--use-hsdp --hsdp-shard-size 8` fits; the per-layer weight gathers cost it 13% against sglang.

**Trainium2: 1× trn2.48xlarge** (16 chips / 64 NeuronCores, LNC=2), SDK 2.33 DLAMI venv (vllm 0.29.0, vllm-neuron 0.29.0.1.2.0, vllm-omni 0.29.0rc1, neuronx-cc 2.28.7631), `vllm serve --omni`, TP8 × CP8. `req_neuron_aligned.sh` (the same requests against the Neuron server).

| tree | config | method | `t2va` | `t2va_parrot` | `t2va_atnight` | `fl2va` |
|---|---|---|---|---|---|---|
| #466 head (`860f5304`) | SP off, AdaLN cache on | 90 s between requests | **53.61 s** | | | n/a (pre-#436) |
| #466 head (`860f5304`) | SP off, AdaLN cache on | back to back | 54.21 s | 54.00 s | 54.53 s | n/a (pre-#436) |
| **staging + #466 + #482, #456 reverted (`8f0d357c`)** | SP on, AdaLN cache on | 90 s between requests | **46.93 s** | | | **52.39 s** |
| staging + #466 + #482, #456 reverted (`8f0d357c`) | SP on, AdaLN cache on | back to back | 52.59 s | 52.36 s | 53.07 s | **59.98 s** |

- **Back to back, Trn2 slows request after request; 90 s gaps remove it.** On `8f0d357c` the five t2va requests take 47.9 / 49.0 / 52.4 / 56.3 / 57.5 s (+20% by the fifth, outputs byte-identical), fl2va 54.0 → 64.5 s. On `860f5304` (SP off) the drift is +2.3 s. A long idle (the 3-minute compile before a new prompt length) resets it: the next request is back at ~48 s. This points at power or thermal throttling under sustained load; it is not yet confirmed. The GPU rows show no drift (stdev 0.01–0.05 s).
- `8f0d357c` is the latest `neuron-staging` (with #436 fl2va) plus vllm-omni-neuron #427 / #418 / #466 and #482 (scheduler step on the device), with #456's vLLM 0.32 upgrade reverted. vllm-neuron 0.32 is not on PyPI, so this is how fl2va runs on the SDK 2.33 venv. For H3 only two call sites differ: `merge_multimodal_embeddings` and the VAE's `init_distributed`.

## The 2026-10-21 rows, and machine-to-machine spread

The same software and request run on different p5en instances differ by ~9%. vllm-omni 0.29's `t2va_atnight` output was byte-identical (md5 `9a62c2d9eed5`) on 2026-10-21 (42.96 s, driver 595.91.07) and on 2026-11-02 (39.16 s, driver 595.112.07), and sglang moved by the same amount (41.81 → 37.71 s). So the earlier note that "sglang `dev` itself got faster" was wrong: the instance (and possibly the driver) did. Today's H200 box (37.98 s) agrees with 2026-11-02. A cost or ratio claim built on one H200 run carries this ±5%.

**8× H100 80GB**（p5.48xlarge spot，us-east-2b，驱动 595.112.07）。

| 栈 | 并行 | `t2va` | `t2va_parrot` | `t2va_atnight` | `fl2va` | 每卡峰值 |

**Trainium2：1 台 trn2.48xlarge**（16 芯片 / 64 NeuronCore，LNC=2），SDK 2.33 DLAMI 环境（vllm 0.29.0、vllm-neuron 0.29.0.1.2.0、vllm-omni 0.29.0rc1、neuronx-cc 2.28.7631），`vllm serve --omni`，TP8 × CP8。

## 2026-10-21 的数据，以及机器之间的差异

同一软件、同一请求在不同 p5en 实例上相差约 9%：vllm-omni 0.29 的 `t2va_atnight` 输出在 10-21（42.96 s，驱动 595.91.07）和 11-02（39.16 s，驱动 595.112.07）逐字节相同（md5 `9a62c2d9eed5`），sglang 也同幅度变化（41.81 → 37.71 s）。所以之前写的“sglang `dev` 本身变快了”是错的，变的是实例（可能还有驱动）。今天这台 H200（37.98 s）与 11-02 一致。基于单次 H200 测量的成本或倍数结论，都带着这 ±5% 的不确定性。
